# Dungeon SK — Decisions

Durable design and architecture decisions with rationale. Update this file when a choice would be hard to reverse or non-obvious to a future maintainer.

## Architecture
- **Vanilla ES6, no build step, no external assets.** All art is generated from ASCII matrices or canvas primitives at runtime; all audio is synthesized. The game runs from a static folder.
- **Classic scripts + `window.SK` namespace instead of browser ES modules.** `type="module"` is blocked by CORS on `file://` in every major browser, but the brief requires launching by opening `index.html` *and* serving locally. Each file is an IIFE registering classes into `SK`, keeping modular boundaries with zero build and working in both modes. This is the one intentional deviation from a literal "ES6 imports" reading; deterministic launch matters more.
- **480x270 design resolution, full-window responsive presentation.** The playfield keeps a fixed 270px virtual height, so every vertical HUD/world measurement is identical at all window sizes. The virtual width is 480px on windows at or narrower than 16:9 and widens (even pixel values, capped at 640px) on wider windows, revealing more of the level instead of stretching or cropping it. CSS scaling is continuous rather than integer-snapped, so the canvas reaches the window edges; `image-rendering: pixelated` plus `imageSmoothingEnabled = false` keeps nearest-neighbour sampling, and integer `left`/`top` offsets keep the upscaled grid on whole device pixels. When `VH × aspect ≤ 640` the canvas covers the viewport exactly (the ≤0.2% aspect error from rounding the virtual width to an even integer is spread across the window); otherwise it is uniformly contained. Rationale: integer-only scaling wasted a quarter of a 1080p browser window and left bars on all four sides, while stretching would distort the pixel art and cropping would hide the HUD.
- **The interface has its own pixel grid at half the world's pixel size.** The HUD keeps its original 480x270 design coordinates, but one UI pixel covers half a world pixel, so the whole interface renders at 50% of the world's on-screen scale. Clusters are anchored independently (top-left, top-centre, top-right, bottom-left, bottom-centre, bottom-right, centre) with `Game.uiLayer`/`withUI`, so panels stay glued to the screen edges at any virtual width without moving any layout constants. The backing store is doubled (`UI_SCALE = 2`) and the world is drawn with a 2× transform, so both grids stay nearest-neighbour crisp; the UI draws 1:1 in backing pixels. Hit testing converts the mouse into each layer's design space (`uiMouseIn`) rather than duplicating rectangles. This costs a 4× fill area (still 60 fps) but gives a clean, uniform 50% interface without cropping, stretching or re-authoring the HUD art.
- **Fixed timestep 1/60 s with an accumulator.** Rendering happens every rAF; simulation catches up in fixed steps (max 6 per rendered frame) so movement/timers are stable. `dt` is clamped to 0.1 s after tab switches.
- **Coordinates:** world pixels, 16 px tiles, feet-anchored entity positions. Camera offsets are rounded before drawing to avoid shimmer; sprites are 1x canvases blitted with smoothing disabled.
- **State lives in one `Game` controller** (`main.js`), with presentation split into `Dungeon`, `Player`, `Enemy`, etc. Entities query the game for collision/targeting, which keeps collision ownership centralized and avoids circular module imports.

## Dungeon generation
- **Six rooms, straight 3-tile-wide corridors.** Spawn, three combat rooms, portal and one branching treasure room. Rooms grow outward from an existing room in a cardinal direction. Each new room is placed with at least a 3-tile shared doorway span, so corridors are perfectly straight and gates sit exactly across a 3-tile opening. Layouts vary in room sizes, distances, growth order and shape. A hand-authored cross-shaped fallback is used if random placement cannot finish (very rare; forced in tests).
- **Treasure branch selection:** the treasure room is a leaf of the room tree attached to a non-spawn, non-portal room, which guarantees its parent becomes a combat room. The portal is then chosen as the farthest remaining room (excluding the treasure and its parent), so the treasure never sits on the portal path. A pre-marked fallback treasure room is preserved. Verified over 800 seeds.
- **Room types/contents:** spawn and treasure are safe; portal is safe and holds the exit; three combat rooms hold the fights. The treasure room contains one gold chest at its exact centre and no enemies/crates.
- **Room sizes:** spawn 16–19×10–12, other rooms 16–20×10–13 (interior tiles). Rooms are kept at least 3 tiles apart. The map grid is 96×64; camera clamps to actual content bounds (with 24 px breathing room), not the whole grid.
- **Walls are derived, not authored:** after carving floors, any void tile 8-adjacent to floor becomes wall. This makes arbitrary joins watertight. Void beyond that is covered by a very dark bedrock tile so rooms read as embedded in rock rather than floating in black.
- **Doorway gates belong to a room side.** A combat room gets one gate per connected side; gate collision is one tile deep × three tiles wide. Spawn, portal and treasure rooms have no gates. When locked, gates are red with a cyan centre beam; when retracting they turn cyan. Bullets and movement are blocked by active gates.
- **Room trigger = the player's whole collision AABB inside the room interior.** This prevents trigger/relock flicker while standing in a doorway.
- **Combat contents:** 2–4 crates, 3–4 goblins (always at least one Guard and one Shaman) and 1–2 Crystal Turrets on depth 1, scaling with floor depth (see Milestone 4 decisions). Enemy/crate spots avoid room edges, door mouths and each other. The room centre is reserved for the post-clear chest. Turrets are placed before crates so the occupied-tile set keeps them apart.
- **Chest spawns at the exact room centre.** Content generation keeps the centre clear. A cleared combat room spawns a normal `Chest`; the treasure room spawns a `gold` chest on floor load. Both open on player contact.
- **Portal at the portal-room centre**, with a trigger radius of 15 px around the player's torso. Advancing regenerates a floor at `depth+1` and preserves the player's carried stats/weapons/slots.

## Combat / feel
- **Collision boxes smaller than art:** player 10×8, goblins 12×10, crates 14×14 inset, bullets 2.5 px radius. Movement is sub-stepped and axis-separated, giving correct sliding against walls, crates and gates.
- **Auto-aim is sticky + predictive.** The nearest enemy within 160 px with clear LOS (walls, closed gates, crates) is acquired; the current target is kept while still valid to avoid flicker, and shots lead moving targets using their previous-frame velocity. If no target, aim is the last normalized movement direction. This satisfies the brief and feels better than re-picking every frame.
- **Crates count as cover for LOS/auto-aim** because bullets are blocked by them; locking onto enemies through unbreakable cover caused wasted shots in testing.
- **Sword hit rule:** a sector at range 34 px, ±62°, applied once ~0.045 s into the 0.19 s swing. The same sector continuously deflects enemy bullets while the swing is active (≤0.17 s), spawning sparks and 2 px shake. Crate hits use a slightly expanded range (38 px). The scythe and greatsword use the same rule with per-weapon range, half-angle, damage and swing duration from the registry.
- **Projectile removal order:** walls → gates → crates → targets. This prevents bullets crossing an active gate line or punching through corners. Hostile bullets are removed by gates/crates too.
- **Player stats/timers:** armor absorbs integer damage first; remaining damage hits HP. One `iframes` window (0.85 s) prevents multi-hit bursts. Armor regen tracks time since last damage (3.5 s) then +1 / 0.8 s; any hit resets both timers. HP only changes via damage or potions (+2). Energy is a capped 200 pool.
- **Potion collection is blocked at full HP** so the +2 heal isn't wasted; the potion remains on the floor. Energy orbs are always collected (a full bar just means no gain) because they are the primary feedback for kills.
- **Notice banners** are short and centered near the room action (`ROOM SEALED`, `ROOM CLEARED`, floor entry). Room-clear banners can briefly overlap the chest, but the chest is contact-opened immediately underneath, so no interaction is lost.
- **Juice:** white flash sprites generated from the same matrices, floating pixel damage numbers, muzzle star, bolt trails, screen shake on deflects/breaks/hurt, hurt vignette (red for HP, blue for armor), low-HP heartbeat vignette.
- **Difficulty scales per floor, driven by one curve.** `SK.Difficulty` (`difficulty.js`) owns the enemy HP multiplier and combat-room spawn ranges; the dungeon generator and live `Enemy` stats both read it, so content and combat can never disagree. HP is `+20%` of base per floor (linear, rounded), goblins gain +1 per two floors (cap 7–8) and turrets +1 per three floors (cap 3–4). Damage, fire rate and bullet speed are deliberately **not** scaled, keeping every existing telegraph fair. Depth 1 resolves to the original Milestone 3 tuning exactly.

## Presentation / art
- **Baker-generated 1px outlines.** The art matrices are fill-only in most cases; `bakeSprite` writes `#0a0c12` into transparent cells adjacent (8-way) to opaque pixels. This guarantees an unbroken outline around silhouettes and transparent gaps (legs, staff) without hand-maintaining every border pixel. Palette rows remain ASCII grids; invalid widths throw with a sprite name.
- **2–3 shades per material.** Player hood 2 (`W/w`), robes 2 (`d/e`), gold 2 (`g/G`), skin 2; goblin green 3 (`1/2/3`), vest 2; shaman purple 3; steel weapons 3; wood 3 (`h/o/O`); floors 3. No checkerboard dithering.
- **White flash variants** are generated by replacing all non-outline opaque pixels with white and cached alongside the base canvas.
- **Pixel font instead of a web font.** A 5×7 bitmask font covers A–Z, 0–9 and UI punctuation, drawn with fillRects. This keeps the UI sharp and avoids external font URLs.
- **Pistol readability:** the first tile iteration looked like a blade in-hand. The final 18×10 pistol is a short, dark, L-shaped slide with a prominent brown grip and a 1×1 hand pixel, and it is positioned further from the body. The sword is deliberately much longer and brighter with a gold crossguard, so the two silhouettes read instantly.
- **Rarity weapon silhouettes:** the shotgun is a chunky double-barrel with a wide wooden stock/pump so it reads differently from the pistol; the railgun is a long white/slate body with a bright cyan core; the scythe uses a thin curved crimson crescent on a dark shaft; the greatsword is a wide crystalline green blade with a gold crossguard. All use the same baker-generated outline and 2–3 cel shades.
- **Gold chests** reuse the hand-authored chest matrices with a gold palette, keeping the silhouette instantly recognizable while the palette and stronger glow communicate higher value.
- **Crystal turret** is a stone trapezoid base with a faceted magenta crystal; its telegraph adds only light/ring effects so the underlying sprite stays crisp.
- **Player face is pale skin in a shadowed cowl** (not a black visor) so the 1×2 cyan eyes read as a hooded person rather than a space helmet. Flipping is applied around the feet; the weapon rotates independently toward the aim vector.
- **Environment contrast:** floor `#343946` slate with sparse seam/crack variants, wall top `#52596b` + front `#252934`, and a near-black bedrock backdrop. Characters, gold trim and cyan/red glows are the brightest elements.
- **2.5D walls:** 16×24 sprites (16 top + 8 front lip), drawn row-major so a lower wall's top face hides the front face above it. Entities are drawn after walls, so a character standing south of a wall appears in front of its dark lip.
- **Portal:** larger-than-life by design—pixel dais, rune ring, converging swirl rings, light plume, rising motes and a strong gradient glow. It is the focal point of an otherwise quiet room and the only always-blue landmark on the minimap.

## HUD / UX
- HUD (top-left) uses icons + explicit labels + segmented bars + values so it reads at 1x and 3x: HP 6/6 red, AR 5/5 blue, EN 200/200 yellow.
- Minimap (top-right) is translucent, always shows the portal, uncleared-room pips and the gold treasure-chest icon, brightens rooms the player has entered, draws actual corridor rects, highlights the current room with white corner brackets, and shows the player dot.
- Floor badge (`FLOOR 1-1`) top centre; weapon slots bottom-left with keycaps, icons, rarity-coloured active name, energy-cost bolt badge and cooldown fill; a short first-floor control hint fades after 12 s.
- Notices use the same 5×7 font and a dark strip so they remain legible over walls.
- Start/pause/game-over overlays are drawn in the virtual canvas, so they scale and pixelate with the game. All use the same font and gold/slate accent palette.

## Audio
- **Tiny WebAudio synth, no assets.** Separate tone/noise helpers with per-effect envelopes and rate limiting. Audio context is created/resumed only on a user gesture; if it is unavailable every path is guarded.
- **Milestone 2 sounds** are synthesized in the same table: shotgun noise burst, railgun sweep/zap, heavy scythe/greatsword whooshes, crescent-wave noise, turret charge whine, turret volley, pickup-equip arpeggio, dry-fire click and a four-note treasure fanfare.
- `M` toggles mute; the choice persists via localStorage in a try/catch (file:// may deny it). The HUD shows `MUTED [M]`.
- Audio property on `Game` is named `audio`; the convenience method is `sfx(name)`. This avoids a property/method name collision that froze the loop during development (see `ERRORS.md`).

## Milestone 2 decisions

### Weapons & energy
- **One data-driven registry, not per-weapon classes.** `WEAPON_DEFS` holds name, kind (`ranged`/`melee`/`beam`), rarity, energy cost, cooldown, damage, sprite, grip offset, muzzle data and behaviour payloads (`shot`, `beam`, `slash`, `wave`, `fan`). The player, HUD and loot systems read the same objects, so a new weapon is data plus a sprite rather than branches in five files. Duplicate weapon references are safe because definitions are immutable.
- **Beam is instantaneous, not a fast bullet.** The railgun ray-marches in 2px steps until a solid tile or locked gate, then damages every enemy whose centre projects onto the segment within `enemy.w/2 + 3px`. This guarantees wall occlusion and true line piercing without tunnelling. Crates along the line take damage but do not stop the beam. A separate `Beam` render entity holds the 0.18s trail.
- **Melee waves are real projectiles.** The scythe wave and greatsword bolts reuse `Bullet` with `pierce` and a per-bullet `hits` Set, so piercing waves cannot double-hit the same enemy. The scythe wave has 6 damage and pierces; greatsword bolts are non-piercing 5-damage fan shots. Both spawn on the same 0.045s beat as the melee hit, so the visual and damage feel synchronized.
- **Enemy knockback is a parameter, not a type check.** `Enemy.takeDamage(..., knockback)` scales the existing impulse; shotgun pellets pass 1.5×. Stationary turrets ignore knockback.
- **Energy is spent at attack start.** This includes melee swings, so a swing can never be free after the energy is gone. Insufficient energy short-circuits before cooldown is set, plays a click/shake, floats `NO ENERGY!`, and starts a 0.4s dry-fire suppression. The HUD energy bar flashes red; the cost badge is red whenever the active shot is unaffordable.
- **Weapon costs keep the M1 200-energy pool.** Costs 2–4 are intentionally small relative to the pool because the milestone brief specifies both; the economy tension comes from sustained turret/ring fights and the fact that orbs are the only refill. Revisit max energy only if a future milestone lengthens floors.

### Inventory & loot
- **Two slots are actual weapon objects, not indices into the starting pair.** `player.weapons = [def, def | null]`; slot cooldowns stay separate. Q/RMB swaps only when both slots are filled, 1/2 ignores empty slots, and all firing/HUD code reads `currentWeapon()`.
- **Pickup semantics are intentional:** with an open slot, the weapon fills it and becomes active; with both slots full, the new weapon replaces the active slot and the old def is spawned as a `GroundWeapon` at the player's feet. Duplicates are allowed. The ground item nearest the player within 22px wins when several overlap.
- **GroundWeapon is a lightweight floor entity.** It uses the feet position, a 1.2px sine bob, a contact shadow, a rarity-coloured radial glow plus a pixel floor ring, and a screen-space `[E] NAME` nameplate drawn after entities so it cannot be hidden by the player. Tossed drops use a short damped velocity and bounce off solid pixels.
- **Chest tables are explicit and testable.** Normal chest = orbs + exactly one of potion or weapon; combat weapon rarity weights are 52/30/18 (common/uncommon/rare). Gold chest = orbs + exactly one guaranteed weapon with 38/34/20/8 (uncommon→legendary). `SK.Weapons.random('combat'|'gold')` is the single RNG entry point, used by chests and tests.
- **Gold chests are visually distinct.** A gold-chest palette bake, a stronger/wider glow and gold glints; the minimap uses a pulsing gold chest pip instead of the portal marker.

### Treasure room
- **Treasure is a true branch, not a converted combat room.** The layout still builds six rooms; designation picks a leaf whose parent is not the spawn, then picks the portal excluding the treasure and its parent. That leaves exactly three combat rooms. The treasure room has no gates, no enemies and no crates.
- **Treasure chest is spawned at floor load** (not on room clear), because the room is never locked and has nothing to kill. Contact opening and the normal loot/ground-weapon flow apply.

### Crystal Turret
- **Turrets are Enemy instances with `stationary: true`.** They reuse room ownership, activation, targeting, hit flashes, health bars, kill rewards and room-clear counting, while returning early from the movement/AI path. This avoids a parallel hazard system and keeps room clear logic unchanged.
- **Telegraph is deliberately generous:** 0.55s of a bright core flash plus an expanding dotted ring, then exactly six 56 px/s purple orbs at 60° spacing with a rotating offset per volley (2.35–3.0s cadence). The orbs use the existing hostile-bullet pipeline, so walls/gates/crates block them and any melee swing can slice them. This directly supports the brief's "weave or slice" counterplay.
- **Turrets are 18 HP** (more than goblins) because they are stationary and usually visible; they are placed 2+ tiles from room edges and doors and never on the reserved chest centre. 1–2 per combat room from floor 1-1.

### Presentation/UX
- **Rarity colour usage:** exact palette required by the brief. It colours the active name, slot border, slot corner tick, floor glow/nameplate and drop particles. Rarity labels are not drawn as separate text to keep the 480x270 HUD uncluttered; the colour itself is the tier signal, complemented by the name.
- **Cost badge:** a compact dark badge with the existing bolt icon and the cost number (0/2/3/4), placed immediately after the active weapon name. It turns red when the next shot is unaffordable, matching the dry-fire energy bar flash.
- **Ground prompt:** `[E] WEAPON NAME` with a 1px rarity border, dark pixel plate and centered 5x7 font. The prompt is intentionally screen-legible and can briefly overlap the room-clear banner; the banner fades and the prompt reappears.
- **Pickup feedback floats at `y - 48`** so it clears the ground nameplate at the player's feet.

## Milestone 3 decisions

### Meta save & currency
- **One small JSON record, `dungeonSK.save.v1`, separate from the mute key.** It stores only `gems`, `unlockedHeroes` and `selectedHero`; run state is deliberately not saved. The loader floors gems, filters unknown hero ids, forces `knight` into the unlocked list and rejects a selected hero that is not unlocked, so a corrupt/hand-edited record degrades to a valid one instead of breaking boot.
- **The default save is written on first boot.** Relying on “write when something changes” left brand-new saves absent from `localStorage`; writing at boot makes the persistence contract true from the first frame and keeps the three fields present.
- **Writes happen immediately** on Gem collection, spending, unlocking and selecting. The meta loop is small and a lost Gem due to a tab close would be worse than the negligible write cost. All access is wrapped in try/catch; if `localStorage` is denied the game keeps an in-memory save and remains playable.
- **Gem sources are explicit and visible:** 8% per enemy death, 45% per combat-room reward chest, and a guaranteed `+1` on entering the exit portal. The portal award is delivered through the advance overlay as a floating `+1 GEM!` reward because the world is already fading out. Gems are never dropped by the safe treasure room or home.
- **Gem pickup reuses `Pickup`** with a new `"gem"` type. That inherits the existing magnet, collection and draw loop; its value is fixed at 1, it magnetises at a longer range than energy, and collection calls `game.collectGem` rather than the HP/energy paths.
- **An enemy Gem drop is a bonus, not a replacement for orbs.** The existing energy-drop roll runs first; the 8% Gem roll is independent. Turrets use the same roll.

### Home hub & flow
- **Boot state is `home`, not `start`.** Milestone 3 explicitly requires spawning into the sanctuary; the old title overlay was removed and replaced with the home title/controls hints. The same `HomeRoom` instance is reused when returning home.
- **`HomeRoom` is a separate lightweight room object with the pieces of the `Dungeon` interface the game actually needs:** tile collision (`rectHitsTiles`, `isSolidPixel`), `contentBounds`, empty `rooms`/`connections`, `portal`, and draw hooks. During home state `game.dungeon` points at it, so camera clamping, movement collision and player update work without a parallel movement system. Procedural dungeon generation is never run for the hub.
- **The 22x15 room includes a 1-tile wall border, leaving a 20x13 tile walkable interior.** The footprint is exactly 352x240 px as requested; the border gives the walls, torches and wall props a place to live without making the playable room larger than the specified screen area.
- **Pedestals are non-solid.** Interaction is a 26px radius around the pedestal; blocking the pedestal would make the prompt awkward. The active hero's pedestal is empty and marked with a gold cross; every non-selected hero (including locked Gravito) is drawn idling there, so “previous hero returns to the pedestal” requires no extra moving entity.
- **Hero switching replaces the Player stats/loadout immediately.** `Player.setHero`/`switchHero` reset HP, armour, energy, weapons, cooldowns and skill state at the current position; the selected hero is then persisted. This makes swapping a character genuinely change the run, not just the sprite.
- **Hero cards are screen-space UI anchored beside the nearest pedestal.** They are clamped inside the viewport and drawn after the HUD, so they cannot be hidden by world geometry. Only one card is shown. The card previews locked heroes (name, portrait, stats, weapon, skill) so the 1-Gem purchase is informed.
- **The action prompt follows the brief exactly:** green `[E] UNLOCK (1 GEM)` when affordable, gray prompt plus red `NEED 1 GEM!` when not, `[E] SELECT HERO` for unlocked non-active, `EQUIPPED` for the active hero. The insufficient-gem press also floats `NEED 1 GEM!` at the pedestal and plays a deny sound.
- **Return-home always destroys run state but never meta.** Confirming creates a fresh Player at the home spawn with the selected hero's base stats/starter weapon and clears enemies, floor content, temporary weapons, pickups, effects and run counters. Gems/unlocks/selected hero are untouched. Death uses the same home return (with a game-over summary) so the meta loop is consistent.
- **Confirming is a deliberate modal, not a toast.** The HOME button pauses the game and opens `[Y] Confirm Return Home` / `[N] Cancel`; `H` is a shortcut and the pause panel has its own clickable button. Cancel resumes play without changing state. A modal is appropriate because the action is destructive.
- **The home hero plate moved to the bottom-left.** The first layout put the selected-hero panel over the top-left wall, hiding the bookshelves and weapon racks. The plate now sits on the bottom wall margin, leaving the sanctuary art readable.
- **Death now returns to the hub rather than starting a new run.** This is the natural roguelike meta loop for Milestone 3. The game-over screen shows Gems Collected / Gems Kept and explains that meta is retained.

### Heroes & skills
- **Data-driven `SK.Heroes` registry, immutable definitions.** Name, title, sprite prefix, portrait, base stats, starter weapon id, unlock cost, palette colours and skill data live in one object. The Player, HUD, home cards and debug hooks read the same definitions.
- **Starter loadout is one weapon, not the old pistol+sword pair.** The brief lists a singular starting weapon per hero. The second slot starts empty and the existing ground-loot/two-slot flow fills it normally. This preserves the loot mechanic while matching each hero's identity.
- **Skill timing:** Knight's Overdrive uses `skillActive`/`skillCooldown`: 5.0s active and a 10.0s activation-to-ready cycle. Gravito's Gravity Wells starts a **20.0s activation-to-ready cooldown** on collapse; the black hole anchors for 3.0s after a short recall/formation/travel phase, while passive orbs spawn every 2.5s and keep attacking during the cooldown.
- **`F` / `Shift` is the skill key; `E` remains interaction/loot.** `F` was previously a duplicate pickup key. Removing it from pickup avoids an input conflict and keeps `E` as the single “interact” verb in both the dungeon and the hub. `Q`/RMB swapping and `1`/`2` selection are unchanged.
- **Overdrive affects cooldowns only.** `weapon.cooldown / 1.5` is applied when the attack starts, for ranged, melee and beam. Swing animation duration is untouched, so the sixth-of-a-second cadence benefit is readable without changing hit timing. The weapon-slot cooldown bar uses the reduced max as well.
- **Golden afterimages use a baked gold silhouette (`knightGhost`).** Canvas filters/tints are inconsistent across browsers and can soften pixels; a second bake of the same matrix with a gold palette keeps the afterimage crisp and cheap. The aura is a soft radial gradient plus a pixel ring and sparks, not a filled rectangle, so it doesn't obscure the knight.
- **Skill HUD uses the short name `OVERDRIVE`.** The full “BATTLE OVERDRIVE” plus the remaining-seconds text collided in the 168px panel. The full name remains on the hero info card; the HUD uses `OVERDRIVE`/`GRAVITY WELLS`. Knight shows a radial cooldown wedge + refilling bar + seconds; Gravito shows the orb count (`0/3`…`3/3`, `READY`), a radial next-orb sweep, and `FORM`/`SEEK`/anchored seconds/`FADE` while the black hole exists.

### Gravity Greatsword & Sky Meteor
- **The gravity greatsword is a normal registry weapon.** It can be found as legendary loot and works for any hero holding it; its aura, 5-pip counter and meteor behaviour are driven by weapon data (`gravityAura`, `skyMeteor`) rather than hero checks.
- **The 5-swing counter lives on the Player, not the weapon definition.** Definitions are shared/immutable; per-player state belongs on the Player. Pips are drawn at the feet in the dungeon (hidden in the sanctuary) and the counter resets 0.5s after the fifth swing so the fifth-swing meteor is visible and the next swing starts a new cycle.
- **Meteor targeting uses ground coordinates.** `targetY` is the enemy's feet (or 120px ahead along aim if none is in range). The reticle, meteor destination, crater and shockwave all use that ground point, and splash distance compares enemy feet-to-feet. This fixed an early bug where a double `-10` offset centered the blast 10px above the target.
- **The meteor is summoned at swing start,** not on the damage beat. That lets the 0.42s fall and reticle overlap the weighty 0.56s swing. It targets the nearest alive enemy within 230px without a LOS check, exactly as specified; the fallback point is 120px ahead.
- **Sky Meteor visuals are effect entities.** The meteor/rock/tail/reticle draws in the `"over"` layer; the shockwaves also draw over; the crater is a `"ground"` effect so loot and actors appear on top of it. The shockwave is two `RingPulse` instances (purple outer, white inner) and the debris is exactly 18 particles (12 violet rock + 6 orange sparks).
- **The crater is a fading ground decal** (dark ellipse + radial cracks + a couple of orange glints) rather than a persistent tile change, so the floor stays procedural and the effect naturally expires.
- **The blade aura has two layers:** in-hand local motes along the rotated blade edges and occasional world-space violet/indigo particles while the weapon is held. The in-hand layer guarantees the effect is visible even when idle.

### Gravity Wells (reworked)
- **`GravityWells` is a persistent controller, not a 9s timed window.** It owns the passive orbs and the current black hole. The Player creates it when Gravito becomes active and updates it every frame; there is no `expire()`/active timer. A floor transition calls `clearTransient()` so a world-space black hole cannot leak into the new floor; the orbiting orbs/charge persist with the player.
- **Passive orbs:** one spawns every `2.5s`, up to three, and orbits Gravito at 26px radius / 120° spacing / 2.6 rad/s with the multi-layer halo/event-horizon/core/lightning visuals and 12-point trails. When a visible on-screen enemy exists, an orb breaks orbit and homes at 210 px/s, deals exactly 9 single-target damage on contact, then reforms for 0.75s before rejoining the orbit and hunting again. Orb targets are distributed across visible enemies. Orb attacks pause while the invoked black hole is forming/active, then resume during the 20s cooldown.
- **Target gating:** pressing F requires an alive enemy visible on screen with clear line of sight — the player's actual visible range, not an arbitrary skill radius. The player's current sticky `aimTarget` is preferred when valid; otherwise the nearest visible on-screen enemy is chosen using the same LOS/crate-cover rule. No target gives `NO TARGET` feedback and consumes nothing.
- **Press-to-collapse:** with a valid target and cooldown ready, any missing orbs are spawned immediately until there are three, every orb's attack state is cleared/forced into the formation (including a reforming orb), and a 0.42s recall/spiral-in plays. The orbs are consumed into a black hole and the skill starts a **20.0s activation-to-ready cooldown**. Pressing while forming or while a black hole is active gives `BLACK HOLE ACTIVE`; pressing during the remaining cooldown gives `COOLDOWN`; neither consumes anything.
- **Black hole travel & anchor:** `R = 22`. It launches from the formation point, homes toward the chosen enemy's centre at `260 px/s`, re-aiming at the target's live position during travel, and on arrival deals **20 damage to that tracked enemy** before anchoring for `3.0s`. If the target dies mid-flight, it continues to the last known point. Once anchored it stays fixed (it does not chase the target around). It then fades for 0.45s and is removed.
- **Pull field:** `pullRadius = R × 2.2 × 1.5 = 72.6px` — i.e. 1.5× the outer aura “ball”. While anchored, enemies and stationary turrets inside the radius are moved toward the event horizon through the normal sub-stepped `moveEntity` collision path (so walls/gates block them), with a small tangential swirl. Hostile bullets within the radius have their velocity curved inward. The caster is excluded. The black hole's 20 damage is a focused single-target crush on the enemy it tracked; the pull itself does not deal additional damage. It is both a clump/CC setup and a payoff hit for the 20s cooldown.
- **VFX order is literal back-to-front:** (1) soft periwinkle radial aura at `R×2.2` with a faint 1px lavender ring, (2) two pure-white horizontal crescent flares at 0°/180° out to `R×1.75` plus white→`#a5b4fc` curved upper shoulder wisps, (3) two tapered white/`#e9d5ff` streaks sweeping along the bottom 60°–145° arc, (4) solid `#05010a` event-horizon core radius `R`, (5) tapered `#d8b4fe` inner crescent rim at `R×0.85` from 175°–265°, (6) a curved accretion slash rotating slowly around a ~38° base tilt. The slash is pure white outside the core and `rgba(250,232,255,0.82)` inside it; an even-odd clip cuts the core hole so the white underlay cannot wash out the pink inside.
- **Cel-shaded helpers:** tapered ribbons/arcs/arc-bands are built from sampled quadratic/arc paths with a sine taper. This gives sharp pointed flares, curved wisps and tapered streaks without canvas blur/filters; only the aura uses a gradient, and the core is an unblurred solid fill.
- **HUD:** while a black hole exists it shows `FORM` during collapse, `SEEK` during travel, the remaining anchored seconds (e.g. `2.6S`) or `FADE`; the bar drains over the 3s. During the 20s cooldown it shows the remaining seconds with a radial refill wedge and dimmed icon while the passive orbs keep fighting. When ready it shows the orb count (`0/3`…`3/3`, `READY` at 3) and a radial sweep for the next orb.
- **The old 9s timed skill window is not restored.** Passive orbs once again use the `orbit/return/homing/reform` state machine, target distribution, 9-damage contact and singularity pop/reform. The old 12s cycle is replaced by the **20s black-hole cooldown**; the orbs are persistent and keep attacking during that cooldown.

### HUD / UX
- **Top-right dungeon HUD row is `[GEM count] [HOME]`, with the minimap moved down 18px.** The minimap already owned the corner; moving it down preserves its size and gives the Gem currency and destructive HOME action their own readable, clickable row.
- **Notices moved from y=78 to y=92.** The new skill panel occupies y=62..86; the banner would otherwise overlap the keycap/gauge.
- **Gem counter is icon + integer, no word label.** It matches the HUD's icon language, fits the 480x270 strip, and is instantly readable in both the hub and the dungeon.
- **Hero cards use the 5x7 font and a 2x portrait.** They preview the full kit and are deliberately semi-transparent so the sanctuary remains visible behind them.
- **The start screen is gone.** The hub is the landing experience; the title is now a small “DUNGEON SK / SANCTUARY” header. This is required by “Boot Directly Into the Home Room”.

### Art / technical
- **`bakeSprite` gained `outlineColor`.** Milestone 3 explicitly calls for pure `#000000` outlines on heroes, the gem, the greatsword and the meteor, while the older dungeon art keeps its `#0a0c12` outline. The outline generator still writes only into transparent cells.
- **Every outlined M3 sprite has a 1px transparent margin.** The first hero/gem matrices touched the canvas top/right edge, so the generated outline had nowhere to draw and was clipped. The matrices now leave a margin; an automated edge audit reports zero non-outline art pixels on any audited edge.
- **Home art is baked, effects are procedural.** Floor/carpet/wall/pillar/pedestal/shelf/rack/torch are ASCII-baked with the same baker; flames, light pools, rune rings and portal swirls are canvas primitives so they can flicker every frame.
- **Pixel font gained `%`, `&`, `(`, `)` glyphs.** The 5x7 map silently skipped unknown chars; without these, skill text read “+50  ATTACK SPEED” and modal text lost its punctuation. Unknown chars still render as spacing by design.
- **The home portal is the dungeon portal function.** `SK.drawPortalAt` was extracted from `Dungeon` so the hub and exit portal share one animation instead of duplicating a 140-line drawing routine.

## Milestone 4 decisions

### Difficulty curve
- **One tiny module, `SK.Difficulty`, instead of balance constants spread across the generator and entity code.** `difficulty.js` is loaded before `dungeon.js` and `entities.js`, and exposes pure functions: `hpMultiplier`, `hpPercent`, `scaleHp`, `goblinRange`, `turretRange`, `normalizeDepth`. The dungeon uses the range functions for room content, the enemy constructor uses `scaleHp` for live HP, and the floor notice uses `hpPercent` for its subtitle. A future boss/elite system can extend the same object rather than rediscovering the curve.
- **HP grows linearly by +20% of the base value per floor, not exponentially.** Linear growth is easy to reason about, keeps early floors gentle, and lets damage-focused weapons stay relevant for many floors. Guards go `12 → 14 → 17 → 19 → 22` over floors 1–5; shamans `9 → 11 → 13 → 14 → 16`; turrets `18 → 22 → 25 → 29 → 32`. Values are rounded to whole HP (no fractional health bars) with a minimum of 1. Base `ENEMY_STATS` stays immutable so the curve is applied per spawned instance, and `Enemy` stores the `depth` it was built for.
- **Spawn count growth is stair-stepped, not per-floor.** Goblins use a 3–4 range at depth 1, add +1 to both ends every two floors (first extra goblin on depth 3), and cap at 7–8 on depth 9; turrets use 1–2, add +1 every three floors (first extra turret on depth 4), and cap at 3–4 on depth 7. Per-floor growth would overcrowd the fixed 16–20 × 10–13 rooms and turn deep floors into unavoidable bullet walls; the stair step still makes every second/third floor visibly busier while the HP curve keeps pressure rising each floor. Both caps are room-capacity and readability decisions, not performance ones.
- **The notice percentage is the nominal curve, not re-derived from rounded HP.** `ENEMY HP +40%` on depth 3 is the design value (`0.2 × 2`); a guard's actual 17/12 is +41.7% because HP must be a whole number. Deriving the label from one enemy's rounded HP would be noisier and type-dependent, so the curve is shown and the docs/tests assert the actual rounded per-type values.
- **Counts are rolled with the existing dungeon RNG and `rint`, preserving depth-1 determinism.** At depth 1 the ranges are exactly the old constants and consume the same RNG draws as before (one for the goblin count, one for the turret count) plus the same shuffles, so the 800-seed structural suite still validates the original layout/content contract. New depth tests assert observed counts stay inside the published ranges across seeds.
- **Depth is normalized defensively.** `Dungeon` and `Enemy` both clamp missing, zero, negative or non-finite depth to 1, so debug `new SK.Enemy(...)` calls and hand-built test dungeons keep working without passing a depth. `Enemy`'s new `depth` argument is optional and last, which keeps every historical call site valid.
- **The player learns about scaling from the floor-advance notice.** The subtitle changed from `KEEP DESCENDING` to `ENEMY HP +20%` / `+40%` / …; this is the only new UI. A permanent threat meter would crowd the 480×270 HUD, and the advance overlay is already the moment the player expects a floor summary. Floor 1-1 keeps `DEFEAT THE ENEMIES` because its multiplier is 100%.
- **Only HP and count scale.** Enemy bullet damage, speed, fire cadence and turret ring size are untouched so earlier dodge/slice/cover lessons stay valid and the game remains fair at depth. Elites, bosses and chapter endings remain future scope.

## Milestone 5 decisions

### Hero architecture
- **Two abilities are slot data, not a second hero class.** `HERO_DEFS[hero].skill` is slot 0 and an optional `skill.skill2` is slot 1. `activateSkill(game, slot)` dispatches by skill id; `F` passes 0 and `Shift` passes 1. Heroes without a `skill2` fall back from slot 1 to slot 0, so Knight and Gravito keep their old single-key behaviour and the change is invisible to them. Per-ability state lives on the Player (`rift*`, `phase*`) rather than on immutable definitions.
- **Hero art size is data.** `spriteW`, `spriteH` and `ghost` are optional hero fields; Player draw offsets, shadow width, afterimages, `centerY`, idle pedestal art, hero-card portrait frames and the home selected plate read them. The Traveler is 24x28; the existing heroes remain 20x22 and need no changes. `centerY()` moved from the hard-coded `y - 11` to `y - artH/2`, which keeps aim/melee geometry correct for both sizes.
- **The Traveler is a free base hero.** A brand-new save starts with `knight` and `traveler` unlocked. `loadSave` also pushes `traveler` into any older save that lacks it, without touching `selectedHero`, so existing players get the new hero immediately and the home room never shows a defunct pedestal.
- **Three pedestals, spaced by screen position.** Knight/traveler/gravito sit at tiles 6/11/16 on the carpet, 80px apart, so the 26px interaction radius and the name plates never collide. Hero cards now choose left/right by `screenX < VW/2` rather than a hard-coded `knight` check, and unlock copy/VFX use the hero's own name/cost/colors.

### Kamui Rift
- **The rift is a four-state player machine:** `normal → entering → rift → exiting → normal`. Entering/exiting are committed 0.8s two-phase sagittal spins that lock movement and attacks: the first 0.36s spins and shrinks the traveler to a point, a brief dot-sized pause follows, then the remaining 0.36s spins again and grows them back in the destination dimension. The state transition happens at the end of the second spin. F during a spin is ignored. The exit starts the 6.0s cooldown; the dimension itself has no time limit because the brief defines the exit as a second key press.
- **Only the player loses collision.** `Player.update` swaps its movement/knockback predicate for `() => false` while `isInRift()`. `Game.isBlocked` is untouched, so enemies, black-hole pull, hostile bullets and every other entity still collide normally. This avoids the catastrophic alternative where a global noclip would de-collide the whole simulation.
- **The camera unclamps only for the rift.** `updateCamera` keeps the usual content-bounds clamp for normal play (including the home room's centred 352x240 layout) but centres on the Traveler and ignores room bounds while `isInRift()`. Without this the player would walk through a wall and off-screen.
- **Exiting searches for a safe tile.** `Game.findFreeSpot(x,y,96)` checks tile collision, gates and crates at the current pixel, then samples 16 angles at 8px steps up to 96px, falling back to the floor spawn point. This prevents the classic "unphase inside a wall" hard lock.
- **The portal is a world effect, not a screen shader.** `SK.KamuiVortex` lives in `game.effects` with `layer:"ground"`, so it draws behind pickups/actors and the player can spin in front of it. The entry portal opens over 0.18s, holds 0.86s and closes over 0.26s: it is fully closed 0.5s after the 0.8s entry completes (close runs from 1.04s to 1.30s). The exit portal uses a shorter hold; enemy banish portals are radius 34 and last slightly past the pop.
- **The light-purple wash is deliberately translucent.** `SK.Kamui.drawRiftOverlay` uses a flat lavender fill plus a soft radial edge and drifting motes, layered after the world and before the HUD. It ramps with the entering/exiting spin. Early values washed the black vortex out; the final values keep the environment readable while making the dimension unmistakable.
- **Enemies are blind, not merely unable to damage.** `Enemy.update` returns early (zero velocity, cancelled charge) while `player.isUntargetable()` is true. Damage is also blocked at the real choke points (`Player.takeDamage`, hostile bullet overlap and contact damage). This is the literal reading of "enemies cannot see or hit the player".

### Intangibility
- **Timed window instead of a toggle.** 4.0s active on a 9.0s activation-to-ready cycle. It is deliberately shorter than the rift and cannot be used inside it. Enemies keep targeting and firing; only the player's damage receptor is disabled. Walls remain solid.
- **Eye-originating VFX, not a second portal.** `SK.Kamui.drawEyeTrails` emits 12 broken spiral ribbons from the actual eye pixel (facing-aware), with per-trail speed, radius, span, width and opacity, plus a faint pale edge so dark tendrils read against dark floors. There is no closed outer boundary, no dense vortex and no face-covering fill, matching the second reference brief.
- **The effect is drawn after actors.** `Player.drawSkillWorld` renders the eye trails after the y-sorted actor pass, so tendrils overlap nearby enemies and props instead of being clipped behind them. The player body itself uses a lower alpha plus a small eye halo.

### Kamui Gloves
- **A new `summon` weapon kind.** `tryAttack` dispatches it before the melee fallback; it never creates a `swing` or a `Bullet`, so no sector damage or muzzle flash can leak through. The data carries `cooldown:2.0`, `energyCost:0`, `execute:true`, `damage:9999` and a `summon` block (range/radius/spin time).
- **Banish is an on-enemy state, not an instant kill.** `Enemy.beginBanish` freezes the AI and sets `banishing`; `Enemy.drawBanish` applies a sagittal-axis spin plus uniform shrink over 0.9s; `Enemy.update` pops the target with a ring/particles, floats `BANISHED!`, then calls `die()`. The room-clear test keeps counting the enemy as alive until that pop, so the chest cannot appear while the animation is still playing.
- **Banished enemies are skipped by every target list.** Auto-aim (`findAimTarget`), friendly bullets, melee, beams, Sky Meteor, Gravity Wells targeting and black-hole pull all ignore `banishing`; `Enemy.takeDamage` also returns early. This prevents a second weapon or orb from stealing the kill mid-animation.
- **The target is executed, not damaged.** The combat numbers stay readable (no `9999` float); the kill is delivered by `die()` after the spin. The `damage`/`execute` fields are documentation and future-proofing for a boss system.
- **No-target fire is a short retry.** A cast with no visible enemy creates no world portal, shows `NO TARGET` and resets the slot cooldown to 0.45s instead of consuming the full 2s. LOS and crate cover use the same `targetVisible` rule as every other weapon.

### HUD / art / module layout
- **`kamui.js` is a separate visual module loaded after `sprites.js`.** The vortex, eye tendrils, rift overlay and `KamuiVortex` effect are large procedural drawing routines; isolating them keeps `entities.js` about gameplay and lets the portal be tuned without touching weapon code. It registers only `SK.Kamui` and `SK.KamuiVortex`.
- **Two-row skill panel only when needed.** Dual-ability heroes get a 184x48 panel with two 24px rows and `F`/`SHIFT` keycaps; single-ability heroes keep the original 168x24 panel and keycap position. Notices move from y=92 to y=116 only for dual-ability heroes, and the debug panel shifts down with them.
- **The vortex is drawn with layered canvas paths, not a bitmap.** Ten spiral ribbons rotate at different speeds (outer slow, inner fast); six heavy broken ink bands add the thick reference-style rings; a grey radial haze, outer smoke arcs, inward-flow specks and a stable black centre complete the effect. All parameters are deterministic from a per-portal seed, so the portal animates smoothly instead of flickering random pixels.
- **The Traveler sprite is hand-authored 24x28.** The mask spiral is generated procedurally then baked as a static matrix, and the garment is hand-placed to keep the mask/eye readable at 1x. The red/black glove is 18x13 with four claw fingers, a spiral backplate and a violet rift glint.


- Sprite art was iterated with a throwaway Python/PIL preview sheet, then the final matrices were baked by the actual JS baker and reviewed in-game.
- Runtime verification uses headless Chromium (Playwright) with console/page error capture, screenshots, state inspection through `window.__dungeonSK` / `window.DungeonSK`, and both HTTP and `file://` origins.
- The dungeon generator has a structural/content stress test (800 seeds), a fallback-layout test, and dedicated chest-roll distribution checks.
- Memory docs (`PROGRESS.md`, `DECISIONS.md`, `ERRORS.md`, `TESTING.md`) are updated as the source of truth for project state.

## Milestone 6 decisions

### Cancellable Intangibility
- **Second Shift press is a cancel, not a denial.** `activatePhase` checks `phaseActive > 0` before the rift/cooldown checks and calls `cancelPhase`. Cancelling immediately zeroes `phaseActive`, so `isInvulnerable()` is false and `canAttack()` is true on the same frame; `phaseFx` fades out over ~0.24s so the eye tendrils collapse instead of popping. `SOLID!`, a collapsing eye ring and a new `phaseOff` sound confirm the action.
- **No cooldown refund.** The 9.0s cycle keeps counting from the original activation. Refunding or shortening the cooldown would make "phase, shoot one burst, cancel, re-phase" a near-permanent invulnerability loop. The intended trade is explicit: cancel early to regain your weapon, and pay for it with the rest of the cooldown. A cancel during the rift also works (the phase timer runs independently there).
- **The HUD reads the state, not a new flag.** Because cancellation is just `phaseActive = 0`, the existing phase row immediately switches to the cooldown display; no HUD branch was added.

### Kamui Gloves mega portal
- **A successful-cast counter, not a keypress counter.** `kamuiCasts` advances only when a normal cast actually banishes a target. A no-target cast already has a 0.45s retry and `NO TARGET` feedback; letting it charge the mega would turn the counter into a free "spam at empty air" meter. On the third successful cast the player gets the mega, and the counter resets to 0. `setHero`/`switchHero` reset it.
- **The mega is a projectile with enemy-first collision.** Firing at the aim angle and only blooming at max range made a well-aimed shot sail past its target and waste the charge (caught by the first focused test). `KamuiMegaPortal` now checks living, non-banishing enemies inside its flight radius before tile/gate/crate collision, snaps the bloom to that enemy and stops. Walls and cover still bloom it early at the last valid position, so aiming into geometry is a legitimate (if wasteful) decision.
- **Splash is an execute without a damage number.** The gloves' fantasy is "infinite damage", and deep waves have hundreds of HP. `Enemy.kamuiSplash` kills any enemy whose HP is at or below the splash value without floating `9999`; it falls back to `takeDamage` for hypothetical future bosses. The portal also sets caught hostile bullets dead and breaks crates, which makes the bloom feel like a real rift rather than a flat AoE circle.
- **The mega config is weapon data.** `summon.mega` carries speed, radius, bloom radius, range, splash, hold and close; `castKamuiGloves` reads it. A future gloves-like weapon can therefore reuse the mega path without branching on the weapon id.
- **Red is a variant of the existing vortex renderer.** `SK.Kamui.drawVortex(..., {red:true})` swaps the haze/ribbon/speck palette to crimson and adds a hot rim, counter-rotating red arcs, lightning cracks and a core flare. The same code powers the mega bloom, its travelling disc and the home rift gate, so the three visuals stay consistent and cheap to tune. The dedicated `KamuiMegaPortal` adds the trail, leading crescent and rotating rune ring around it.
- **Readout: three pips plus a badge.** The weapon slot gained three cast pips (red and pulsing when the next cast is mega) and a pulsing `MEGA` badge next to the energy badge. A `MEGA READY` float fires after the second cast, so the mechanic is discoverable without a tutorial. The pips are drawn after the cooldown overlay so they remain visible while the slot is cooling.

### Endless Wave mode
- **Arena, not a second dungeon.** `SK.WaveArena` exposes exactly the dungeon surface (`isSolidPixel`, `rectHitsTiles`, `lineOfSight`, `segmentHitsRect`, `contentBounds`, `rooms`, `connections`, `gates`, `portal`, draw calls) with empty rooms/connections/gates and a null portal. That keeps every existing system (player collision, enemy AI, bullets, camera, loot, rift, effects, debug overlay) working without mode branches; `Game.mode` only branches the room/portal update, the HUD badge/panel and the game-over stat labels. The arena is 34x19 tiles (544x304) with four 2x2 pillars so the camera moves a little and cover exists; it is slightly larger than the 480x270 design view and much smaller than the 96x64 dungeon map.
- **Wave scaling is owned by `WaveDirector`, not `difficulty.js`.** Floor depth is linear and integer-normalised; waves are compounding. Enemy HP is `1.1^(wave−1) × base`, count is `round(5 × 1.1^(wave−1))`. To feed fractional HP multipliers, `Enemy` gained an optional 6th `opts.hpMultiplier` argument; the existing depth path is untouched. Turrets follow the wave count (one per five waves, max 4) and the total count is capped at 40 from wave 23. The HP curve never caps, so the mode is truly endless even when the roster size is stable.
- **Spawn placement favours space and safety.** Candidate tiles are sampled on a 2-tile grid, filtered for solid floor and a 104px minimum distance from the player, shuffled with the wave-seeded PRNG, then greedily accepted at 26px spacing. A ring fallback guarantees the exact count even if the arena is crowded. Each spawn opens a crimson `KamuiVortex` so a new enemy never "pops in" invisibly. Enemies spawn active, unlike dungeon rooms where they wait for the gate to seal.
- **Rewards and recovery.** Wave clear awards one persistent Gem (mirroring the floor portal), restores one armor point (or one HP when armor is full; armor also regenerates after 3.5s out of combat), saves the best wave immediately, and drops a random gold-tier weapon plus a heart every fourth wave. The between-wave armor trickle is deliberately small: the arena has no chests or crates, so without any sustain deep waves would be a one-way HP drain. The weapon drop keeps the two-slot loot loop relevant.
- **`bestWave` extends the existing save record.** `dungeonSK.save.v1` now also stores `bestWave` (0 by default, floored, ignored if not finite). It is written on every new record (wave clear, death, mid-run return home) and displayed on the home rift prompt and the game-over panel. The schema remains backward compatible; older saves simply get `bestWave: 0`.
- **The rift gate is E-only and deliberately placed.** It floats above Gravito's pedestal at (258, 84), far enough from the blue dungeon portal (>66px) that the two interaction prompts can never appear together. Because entering is a long, committed run, it does **not** auto-start on walk-in like the dungeon portal; the prompt says `[E] ENDLESS WAVES` and shows the best wave. This also keeps the sanctuary's existing "walk into the portal to descend" muscle memory intact.
- **HUD replaces the minimap instead of squeezing a third panel.** The arena has no room graph, so the top-right `MAP` panel becomes an `ENDLESS` panel with wave, enemies left, best, enemy HP bonus and a progress/countdown bar. The top-centre `FLOOR 1-N` badge becomes `WAVE N`. The notice banner, two-row skill panel, gems, HOME button and weapon slots are unchanged, and the panel was made 96px tall so the six text rows and the bar never overlap at the half-size UI grid.

## Open questions / deliberately out of scope
- **Module syntax vs. file:// compatibility:** currently classic IIFEs. If the project later requires a server-only deployment, converting to native ES modules is mechanical but not needed for the brief.
- **Infinite floors with a difficulty curve, no final win screen:** Milestone 4 adds per-floor HP/count scaling and Milestone 6 adds the endless wave trial, but there is still no chapter end/boss; both modes end only in death or a manual return home. A boss/elite milestone can extend the wave director.
- **The endless roster is capped at 40 while HP never caps.** Forty enemies is already a dense bullet-hell in the 544x304 arena and holds 60fps; an uncapped roster would hit triple digits by wave 50. If a future wave milestone adds a larger arena or a "swarm" enemy, raise `SK.Waves.MAX_ENEMIES` and re-run the perf/placement suites.
- **A mega charge can be fired into empty space.** The third cast always fires the portal (it is a projectile), so a mistimed or mis-aimed cast wastes it. This is player agency rather than a bug; the three pips and `MEGA` badge make the armed state explicit.
- **No mobile/touch controls or gamepad:** keyboard/mouse only, as specified.
- **No in-run save system:** only meta is persisted; reloading mid-run returns to the hub with Gems/unlocks kept. Run state is future scope.
- **One-Gem Gravito unlock:** the data model supports any `unlockCost`, but only the required 1-Gem unlock is exposed. A future hero/shop milestone can extend it.
- **Stats carry across floors with no free heal.** Deeper floors now add pressure through HP/count scaling, while chests, potions and enemy energy orbs remain the only sustain. Revisit the HP curve if playtesting shows it outpaces the loot/weapon ramp.
- **Gravity Wells / Sky Meteor ignore walls for their targeting.** Sky Meteor still uses the brief's no-LOS nearest-target rule. The reworked black hole only acquires an on-screen target with clear LOS, then homes through geometry; its pull respects wall/gate collision. Revisit if wall-heavy rooms make either feel unfair.
